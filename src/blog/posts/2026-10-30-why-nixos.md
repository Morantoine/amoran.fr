I run NixOS on three machines: **balrog**, my laptop; **cyboogie**, a server hosting around fifty
services I use every day (photos, passwords, mail, music, documents, a Git forge); and **gila**,
a small box that watches cyboogie and pings my phone when something goes down.

All three are described by one Git repository. There's no configuration hidden on any of the
machines: if it isn't in the repo, it doesn't exist. This post is about what that allows in
practice.

## The whole machine is a text file

On most Linux systems, the state of a machine is the sum of everything anyone ever did to it:
packages installed by hand, a config file edited at 2 a.m., a service enabled and forgotten. On
NixOS, the system is built from a description. Enabling my password manager on the server looks
like this:

```nix
services.vaultwarden = {
  enable = true;
  config.ROCKET_PORT = 8222;
};
```

Running `nixos-rebuild switch` builds the new system from the description and switches to it.
Because the description is code in a Git repository, I get everything Git gives me:

- **History.** `git log` tells me when I changed something and, with a decent commit message,
  why.
- **Review.** Changes to the server are diffs. I can read exactly what a change will do before
  applying it.
- **Search.** "Where did I configure that?" is a `grep`, not an afternoon in `/etc`.

## Every change can be undone

Each rebuild creates a new *generation* and keeps the previous ones. If an update breaks
something, I pick an older generation from the boot menu, or run `nixos-rebuild switch
--rollback`, and I'm back where I was, packages and configuration included.

This matters most for the server, because I deploy to it remotely. My deploy tool,
[deploy-rs](https://github.com/serokell/deploy-rs), has a *magic rollback*: after activating the
new system, it checks that it can still reach the machine over SSH. If I've just broken the
network or locked myself out, the server returns to the previous generation on its own.

## My laptop forgets everything on reboot

This is the part that surprises people most. On my laptop, `/` and `/home` are wiped on every
boot and rolled back to an empty snapshot. Only the paths I explicitly declare are kept, in
`/persist`:

```nix
home.directories = [
  "Documents"
  "Downloads"
  ".ssh"
  ".local/share/fish"
  # …
];
```

This is only possible because the system is rebuilt from its description every time. Programs
that leave files all over my home directory simply lose them at the next boot. Every reboot gives
me a clean machine, and the list of what persists is also an exact list of what I need to back
up. It uses the [impermanence](https://github.com/nix-community/impermanence) module.

## New machines in minutes

gila is a small virtual server. Its disk layout is declared too, with
[disko](https://github.com/nix-community/disko), so the same repository that describes its
services also partitions and formats its disk. Installing it means building the system I
already described. If the provider disappeared tomorrow, I could recreate gila somewhere else and get the
same machine.

My laptop install is documented in the repo as well, down to the btrfs subvolumes and which ones
are wiped on boot.

## A server I can actually maintain

cyboogie runs around fifty services, a mix of NixOS modules and pinned containers. Without Nix I
would never keep up with that. With it, the maintenance mostly happens on its own:

- **Everything is pinned.** Nix inputs are locked in `flake.lock`, and container images are
  pinned to a digest, so the server never changes underneath me.
- **Updates arrive as pull requests.** Every week a job bumps `flake.lock` and opens a PR, and
  [Renovate](https://docs.renovatebot.com/) does the same for container images. Minor image
  updates merge on their own once the checks pass.
- **CI builds all three machines.** On every push and every pull request, my Forgejo instance
  runs `nix flake check` and builds the full system for balrog, cyboogie and gila. A change that
  doesn't build never reaches a machine.
- **Nothing is built twice.** The CI results go into my own binary cache, served by
  [Harmonia](https://github.com/nix-community/harmonia). When I update my laptop, it downloads
  what CI already built instead of compiling it again.

## Secrets live in the repo, encrypted

Passwords and API keys live in the same repository, encrypted with
[sops-nix](https://github.com/Mic92/sops-nix). Each file is encrypted for my own key and for the
SSH host key of each machine. When a machine boots, it decrypts only the secrets it needs, and
they never appear in plain text in the repository or in the Nix store.

## Development environments that set themselves up

The same idea works for projects. A `flake.nix` in a project declares the tools it needs, and
with [direnv](https://direnv.net/) they appear when I `cd` into the directory and disappear when
I leave. My NixOS repo does this for itself: entering it gives me the formatter, the linters and
the deploy tool, and installs the Git hooks that run them.

## What it costs

It would be dishonest to stop there.

- **The learning curve is real.** Nix is its own language, the documentation is scattered, and
  error messages can be cryptic.
- **Some software assumes a normal Linux.** Prebuilt binaries expect libraries in `/usr/lib`,
  which doesn't exist on NixOS. Tools like `nix-ld` cover most cases, but it's still friction.
- **Disk space.** Keeping old generations around costs space until they're garbage-collected.

For me the trade is clearly worth it. I can rebuild any of my machines from scratch, undo any
change, and see exactly what is running where. Next time I'll write about how I organise the
configuration itself, using [den](https://github.com/denful/den).
